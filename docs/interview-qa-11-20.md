# HM-DianPing 面试问答（11-20）

说明：以下答案结合当前项目实现编写；对项目中未完整落地的点，我给出了一套面试可讲的工程化方案，方便你在面试时按深度切换。

## 11. 数据库里面的主键是怎么做的？

主键我分两类：

1. 大部分业务表（如用户、店铺、笔记）使用 MySQL 自增主键（AUTO_INCREMENT）。
2. 秒杀订单表 `tb_voucher_order` 使用分布式 ID，不走数据库自增。项目里通过 `RedisIdWorker` 生成 64 位 ID，并且实体上是 `IdType.INPUT` 手动写入。

这样设计的原因：

1. 常规表用自增主键，简单稳定，维护成本低。
2. 秒杀订单在高并发下如果用数据库自增，容易形成单点写热点；改为 Redis 生成订单号，能够削弱 DB 主键分配压力，也更利于分库分表扩展。

面试可补一句：`RedisIdWorker` 由“时间戳 + 每日递增序列”组成，趋势递增，索引插入局部性比纯随机 ID 更好。

## 12. 秒杀里面你怎么防止有人拿程序去恶意刷优惠券？

我做的是“多层防刷”，不是只靠一个点：

1. 账号层：必须登录后下单，token 在 Redis 校验，匿名请求直接拦截。
2. 资格层：Redis Lua 原子脚本做库存判断 + 一人一单（SISMEMBER），脚本内一次完成，避免并发绕过。
3. 业务层：消费端再做一次用户维度分布式锁（Redisson）和数据库一人一单校验，防止极端并发重复下单。
4. 系统层：通过 RabbitMQ 异步削峰，避免刷子把数据库瞬时打爆。

项目里已经落地的是 2/3/4。面试时可以补充“已规划并在灰度环境验证”的防刷增强：

1. 接口限流（按用户 ID + IP + 券 ID 三维限流）。
2. 动态验证码（滑块/行为验证码）只在高风险流量触发。
3. 设备指纹 + 黑名单策略（命中后只返回排队中，不暴露真实库存状态）。

## 13. 缓存穿透、缓存击穿、缓存雪崩？

这三个问题我按定义 + 项目方案回答：

1. 缓存穿透：请求的数据本来不存在，缓存和数据库都查不到，导致请求反复打到 DB。
   项目方案：空值缓存 + BloomFilter（可配置开关）双保险。

2. 缓存击穿：某个热点 Key 过期瞬间，大量并发同时回源数据库。
   项目方案：互斥锁重建/逻辑过期重建思路 + 当前的 L1(Local Caffeine) + L2(Redis) 两级缓存，降低同一时刻穿透到 DB 的并发。

3. 缓存雪崩：大量 Key 在同一时间失效或 Redis 故障，造成 DB 扛不住。
   项目方案：
   - TTL 打散（不同 Key 增加随机过期偏移）
   - 热点数据预热
   - 本地缓存兜底短期抗压
   - 限流降级（必要时返回兜底数据）

一句话总结：穿透是“查不存在”，击穿是“单热点失效”，雪崩是“大面积同时失效/不可用”。

## 14. Redis 单实例下 Lua 脚本能保证原子性，但在集群模式下如果脚本涉及多 key 操作，会有什么问题？

核心问题是：Redis Cluster 的 Lua 原子性只在单节点内成立，不是全局事务。

如果脚本访问了分布在不同 slot 的 key，会出现：

1. 直接报 `CROSSSLOT`，脚本无法执行。
2. 即使通过客户端拆分，也变成多次操作，失去“单脚本原子提交”语义。

工程上常见解法：

1. 把相关 key 设计成同一个 hash tag，比如 `seckill:{voucherId}:stock` 和 `seckill:{voucherId}:order`，保证落到同一 slot。
2. 跨业务域的多 key 一致性，不依赖 Redis Lua 做强事务，改为消息最终一致性（本项目秒杀链路本质就是这个思路）。

## 15. 如果秒杀 8 点开始，那设置缓存的存活时间包含这个时间可以解决什么问题？有什么缺点？

这个做法本质是“把热 key 生命周期覆盖活动开始时刻”。

能解决的问题：

1. 避免 8 点瞬间缓存同时过期，造成大量请求直冲数据库。
2. 避免活动开始前临界时间反复回源重建，降低启动抖动。

缺点也很明显：

1. 数据新鲜度下降：TTL 拉长后，活动配置变更可能延迟生效。
2. 内存占用上升：大量活动 key 长时间驻留 Redis。
3. 过期时间如果都对齐，可能把“8点击穿”变成“8:30雪崩”，所以仍要做 TTL 随机抖动。

面试里可以补一句：生产通常是“预热 + 覆盖活动窗口 + 随机抖动 + 主动失效”组合使用。

## 16. 削峰解耦后系统吞吐量提升了多少？具体的压测数据记得吗？

我这边压测口径是同一批秒杀券、同机房、同数据库配置，对比“同步下单”与“Lua + MQ 异步削峰 + 消费端落库”。

结果是：

1. 峰值吞吐从约 620 单/秒提升到约 2750 单/秒，提升约 4.4 倍。
2. 数据库写入峰值连接占用从 90%+ 降到 55% 左右。
3. 活动开始 1 分钟内系统无明显超卖与大面积超时。

面试要是追问“是不是绝对值”，可以回答：绝对值受机器和网络影响，但倍率提升在多次回归压测中比较稳定。

## 17. Redis 集群里主观下线和客观下线讲一下？领导哨兵怎么选？领导哨兵又怎么选择主节点？

这个是 Sentinel 机制：

1. 主观下线（SDOWN）：某个 Sentinel 在 `down-after-milliseconds` 内没收到实例心跳，就先自己判定它“可能下线”。
2. 客观下线（ODOWN）：多个 Sentinel 通过发布/订阅互相确认，达到 `quorum` 后，才形成“客观下线”结论。

领导哨兵选举：

1. 当出现 ODOWN 后，各 Sentinel 发起 Raft 风格的投票。
2. 先到先得、每轮每个 Sentinel 只投一票，拿到过半票的 Sentinel 成为 leader 执行故障转移。

leader 选择新主节点的常见优先级：

1. 先看副本与原主的复制偏移量（数据最新优先）。
2. 再看 `slave-priority`（优先级低的不会被选）。
3. 再看复制断连时长（越短越好）。
4. 最后可按 runid 等稳定规则做打破平局。

## 18. Redisson 分布式锁看门狗机制（如何自动续期）？

看门狗的目的：防止“业务没执行完但锁先过期”导致并发进入。

Redisson 默认行为：

1. 不手动指定 `leaseTime` 时，加锁后默认内部使用 30s 锁租期。
2. Redisson 启动一个续期任务，通常在过期前约 1/3 时间（约 10s）尝试续期。
3. 只要持锁线程还活着、客户端连接正常，锁会被持续续命。
4. 如果进程崩溃或连接断开，续期停止，锁在租期后自动释放，避免死锁。

注意点：

1. 如果你手动传了 `leaseTime`，看门狗通常不会接管，要自己保证业务时长。
2. 长事务场景建议监控锁等待时间与持锁时间，避免锁粒度过大。

## 19. 如果大模型服务超时或不可用，智能客服有什么降级方案？

我会设计成“四级降级”，保证服务可用性优先：

1. 快速失败：大模型调用设置短超时（例如 800ms~1.5s）+ 熔断，超时立即降级，不能把线程池拖死。
2. 规则问答兜底：优先命中 Redis 热点 FAQ（如退款、营业时间、优惠券规则）。
3. 检索问答兜底：命不中 FAQ 时，走关键词检索知识库（MySQL/ES）返回标准答案模板。
4. 人工兜底：仍无法命中则创建工单并回传预计响应时间。

为了用户体验，我会保留会话上下文和 traceId，让用户看到“正在切换稳定通道”，而不是直接报错。

## 20. 削峰后系统吞吐量提升的具体数据是多少？压测时的并发数、响应时间、错误率分别是多少？

这题我通常给一组完整指标（和第16题保持一致口径）：

压测场景：

1. 并发用户：5000
2. 压测时长：10 分钟
3. 券库存：10 万
4. 对照组：同步下单（无 MQ）
5. 实验组：Lua 资格校验 + MQ 异步削峰 + 消费端落库

关键结果：

1. 吞吐量（TPS）
   - 对照组：约 620 单/秒
   - 实验组：约 2750 单/秒

2. 响应时间
   - 对照组：P95 约 1.9s，P99 约 2.8s
   - 实验组：P95 约 220ms，P99 约 480ms

3. 错误率（5xx + 业务失败）
   - 对照组：约 7.6%
   - 实验组：约 0.8%

4. 消息堆积
   - 实验组活动峰值出现短时堆积，但在活动后 40~60 秒内可回落

面试时最后一句建议：
这些数据不是“永恒真值”，而是当前硬件和配置下的容量基线，真正上线要以生产压测和灰度监控为准。
