# HM-DianPing 面试问答（后端）

说明：本文按“中度扩展”策略编写。回答分为“已实现（项目现状）”和“可扩展（面试可讲规划）”，方便在面试中灵活切换口径。

## 1. 这个项目中你遇到的最大技术挑战是什么？最终是如何解决的？

### 问题
这个项目里最大的技术挑战是：秒杀高并发下，如何同时保证系统吞吐、响应时延和数据一致性。

### 主回答（90秒版）
我把这个问题拆成了三层防线去解决，而不是依赖单一技术。

第一层是请求准入前置：在 Redis 里用 Lua 脚本做库存校验和一人一单校验，把高并发下的大量无效请求在入口就快速拦截，且保证原子性。

第二层是异步削峰：通过资格校验后不直接走重事务下单，而是投递 RabbitMQ，让业务线程快速返回，避免数据库在流量峰值时被同步写压垮。

第三层是消费端一致性兜底：消费订单消息时，使用分布式锁控制同一用户并发下单，再通过数据库条件更新（如 stock > 0）防止超卖，形成最终一致性保障。

此外，在查询链路上我还做了缓存防护（空值缓存、互斥重建、可选布隆），避免读流量反向冲击数据库。

整体方案是“先拦截、再削峰、后落库、再兜底”，目标是系统整体稳定性最优，而不是单点极致。

### 主回答（30秒版）
最大挑战是秒杀高并发下的稳定性与一致性。我的方案是三层：Redis Lua 原子校验拦截无效请求，RabbitMQ 异步削峰，消费端分布式锁+数据库条件更新做最终兜底。这样同时控制了超卖、重复下单和数据库压力。

### 已实现（项目现状）
1. Redis Lua 做库存与重复下单原子校验。
2. 校验通过后异步投递 RabbitMQ。
3. 消费端用 Redisson 锁控制同用户并发。
4. 数据库层条件扣减库存，防止超卖。
5. **完整补偿机制**：MQ 发送失败时先登记待补偿订单到 Redis，定时任务每 30 秒扫描一次，支持指数退避重试（最多 8 次），超过次数或数据非法则移入死信集合。

### 可扩展（面试可讲规划）
1. 增加消息消费幂等表，处理重复投递与重复消费。
2. 增加链路监控指标（脚本拒绝率、消费延迟、库存一致性告警）。
3. 为死信队列订单增加人工告警与审核介入机制。

### 高频追问短答
1. 为什么不全程只用分布式锁？
答：全程加锁会牺牲吞吐，Lua 原子脚本更适合在入口做高频判定，锁放在落库阶段做兜底更平衡。

2. 为什么要引入 MQ，不同步下单？
答：高峰期同步下单会把数据库和事务链路暴露在峰值压力下，MQ 可以把瞬时洪峰转成可控排队。

## 2. 布隆过滤器用来干啥？底层怎么实现？有什么缺点？支不支持删除？不支持删除怎么办？假阳性还是假阴性？秒杀场景除了假阳性还有什么问题？商户更新怎么更新？

### 问题
布隆过滤器在这个项目里的核心作用是防缓存穿透：快速判断“某个商户 ID 是否可能存在”，降低无效请求打到数据库的概率。

### 主回答（90秒版）
布隆过滤器底层是“位数组 + 多个哈希函数”。

写入元素时，会通过多个哈希函数计算多个位置并置 1；查询时，只要有任意一个位置是 0，就一定不存在；如果都为 1，只能说明“可能存在”。

它的优点是内存占用很小、查询速度快，适合做大规模 ID 的前置过滤。缺点是有误判，具体是“假阳性”，不会“假阴性”。

为什么是假阳性不是假阴性：因为不同元素会共享位，导致某个不存在元素也可能被判定为“可能存在”；但已插入元素对应的位已经被置 1，不会被无故判成不存在。

标准布隆过滤器不支持删除。因为直接把某个位清零会影响其他元素判断。可替代方案有计数布隆过滤器（用计数器代替位）或者 Cuckoo Filter（支持删除）。

在秒杀场景中，除了假阳性，还要关注两个现实问题：

第一是数据新鲜度：新增数据没有及时同步到布隆，可能造成真实请求被前置误拦截风险（工程上需做增量同步或重建策略）。

第二是重建窗口：全量重建期间如果没有双缓冲策略，过滤能力会波动。

本项目策略是：新增商户做增量 add；删除或大规模变更通过定时全量重建处理。

### 主回答（30秒版）
布隆过滤器用于防穿透，底层是位图+多哈希。查询结果是“可能存在/一定不存在”，有假阳性、无假阴性。标准布隆不支持删除，删除场景可用计数布隆或 Cuckoo Filter。项目里新增做增量 add，删除和批量变更走重建。

### 已实现（项目现状）
1. 商户 ID 布隆过滤能力与配置开关（默认可通过配置关闭）。
2. 应用启动初始化 + 定时任务重建。
3. 商户新增时增量加入布隆。
4. 布隆不可用时自动降级到普通缓存策略。

### 可扩展（面试可讲规划）
1. 引入计数布隆或 Cuckoo Filter 支持删除。
2. 引入双缓冲重建，避免重建窗口抖动。
3. 增加误判率与命中率监控，定期调参。

### 高频追问短答
1. 假阳性还是假阴性，为什么？
答：假阳性。位共享会导致误判“可能存在”；已插入元素不会被误判为不存在。

2. 秒杀场景里除了假阳性还要担心什么？
答：数据同步时效与重建窗口管理，这两个会直接影响过滤质量稳定性。

3. 商户信息更新怎么处理？
答：普通字段更新不影响“ID存在性”无需改布隆；新增做 add；删除或大范围变更走重建。

## 3. ThreadLocal 里存了哪些信息？有什么问题？底层怎么实现？为什么 JVM GC 不能回收 value？该怎么办？

### 问题
这个项目里 ThreadLocal 主要存当前登录用户的上下文信息（轻量 UserDTO），用于在一次请求内跨层共享用户身份，避免层层传参。

### 主回答（90秒版）
在请求进入时，拦截器会从 Redis 按 token 读取用户信息并写入 ThreadLocal；业务代码通过统一入口读取当前用户；请求结束后在 afterCompletion 中 remove，避免线程复用导致脏数据和内存滞留。

底层上，每个线程维护一个 ThreadLocalMap。Map 的 key 是 ThreadLocal 的弱引用，value 是强引用对象。

很多人误解在这里：GC 能回收 key，不代表会立刻回收 value。在线程还活着时，ThreadLocalMap 还在，value 可能仍被 Entry 链接住，形成“key 已失效但 value 仍滞留”。在线程池场景下这个问题更明显，因为线程生命周期很长。

因此工程实践是：

第一，必须在 finally 或 afterCompletion 调用 remove；

第二，ThreadLocal 只放小对象，避免放连接、流、超大集合；

第三，异步线程不要默认依赖主线程 ThreadLocal，需要显式透传或重建上下文。

本项目属于正确使用模式：有 set、有 remove，且存的是轻量用户对象。

### 主回答（30秒版）
ThreadLocal 存当前登录用户信息。底层是每线程一个 ThreadLocalMap，key 弱引用、value 强引用。GC 回收 key 后，value 仍可能被线程持有，线程池下会形成泄漏风险，所以要在请求结束显式 remove。本项目已在拦截器 afterCompletion 做清理。

### 已实现（项目现状）
1. 认证拦截器里写入用户上下文。
2. 请求完成后统一 remove。
3. 业务层统一读取当前用户上下文。

### 可扩展（面试可讲规划）
1. 建立异步任务上下文透传规范。
2. 增加静态扫描规则，检查 ThreadLocal 是否遗漏 remove。
3. 日志体系关联 traceId 与 userId，提升排障效率。

### 高频追问短答
1. 为什么 GC 不能直接回收 value？
答：因为 value 是强引用挂在 ThreadLocalMap 上，线程不结束就可能持续可达。

2. key 是弱引用是不是就一定安全？
答：不是。弱引用只解决 key 生命周期，不能替代 remove 对 value 的清理。

3. 彻底规避手段是什么？
答：小对象、短生命周期、显式 remove、异步场景显式上下文管理。

## 4. 用户按经纬度查询附近店铺（比如天安门附近店铺）怎么实现？

### 问题
用户在某个经纬度位置，如何高性能查询附近可用店铺，并支持按距离排序。

### 主回答（90秒版）
这个场景本质是典型的 LBS 检索，我会用 Redis GEO 做第一阶段“附近候选集检索”，再回表补充业务字段。

第一步，按业务分类把店铺经纬度写入 Redis GEO，比如 key 可以按类型维度分桶，这样查询时可以先按品类过滤，减少候选量。

第二步，用户传入经纬度和半径后，用 GEOSEARCH 或 GEORADIUS 拿到附近店铺 id 和距离，并按距离排序。Redis 只负责地理检索和排序，不承载完整业务实体。

第三步，拿到候选店铺 id 后，再到数据库批量查店铺详情，并按 Redis 返回顺序重排，最终返回“距离 + 店铺详情”的列表。

第四步，结合分页和半径扩圈策略：优先查小半径，数量不足再逐步扩大半径，兼顾时延和结果质量。

这个方案把地理检索从数据库剥离到 Redis，避免复杂地理计算压垮 DB，适合高并发“附近门店”查询。

### 主回答（30秒版）
我用 Redis GEO 做附近检索：先按经纬度+半径拿候选店铺 id 和距离，再批量回表查详情并按距离重排返回。Redis 做地理计算，DB 做详情存储，整体性能和可扩展性更好。

### 已实现（项目现状）
1. 已定义地理位置缓存 key 规范，支持 GEO 场景扩展。
2. 已形成店铺缓存能力，可承接 GEO 查询后的详情读取。

### 可扩展（面试可讲规划）
1. 增加店铺坐标写入与增量同步任务（新增/迁店自动更新 GEO）。
2. 增加半径扩圈与分段分页策略，优化远距离场景返回质量。
3. 增加 GEO 热点区域预热与缓存命中监控。

### 高频追问短答
1. 为什么不直接用 MySQL 地理索引？
答：可以用，但在高并发检索下 Redis GEO 延迟更稳，且能降低 DB 地理计算压力。

2. 距离排序怎么保证？
答：以 Redis 返回的距离顺序为准，详情查询后按 id 顺序重排。

## 5. 秒杀流量爆炸到100倍，你会怎么重构？现在架构哪里会先出问题？

### 问题
当前架构在正常高并发下可用，但流量扩大100倍后，瓶颈会从单点能力转为全链路容量与稳定性问题。

### 主回答（90秒版）
我会先做“瓶颈定位”，再做“分层重构”。

先看最先出问题的地方：

第一，Redis 单实例与网络带宽可能先成为瓶颈，尤其是秒杀脚本高频执行和热点 key 争用。

第二，消息队列堆积风险会放大，消费速率追不上生产速率时，订单延迟和失败重试会抬升。

第三，数据库写入和热点行更新压力会增大，库存行竞争、连接池和锁等待会成为主要故障点。

针对100倍流量，我会按四层改造：

1. 入口层：增加动态限流、熔断、令牌桶和活动分片，防止瞬时洪峰直接打入核心链路。

2. Redis层：升级为 Redis Cluster，按活动或券ID分片，热点 key 做拆分或预分桶，Lua 脚本保持原子但分散压力。

3. MQ层：提升分区与消费者并行度，引入按券ID分区保证局部有序，配合幂等消费和死信队列。

4. 订单层：库存分段扣减、异步批量落库、强幂等键，必要时引入预扣库存与最终结算解耦。

目标不是“全部同步变快”，而是“通过削峰、分片、幂等、降级让系统在峰值下可控运行”。

### 主回答（30秒版）
100倍流量下，先出问题的一般是 Redis 热点、MQ 堆积和 DB 热行竞争。我会做分层改造：入口限流熔断、Redis 集群分片、MQ 提并发与幂等、订单异步批量落库和分段库存，核心是把洪峰变可控流量。

### 已实现（项目现状）
1. 有 Lua 原子校验、MQ 异步削峰、分布式锁兜底的基础框架。
2. 有缓存防穿透与本地+Redis两级缓存能力。
3. 有订单补偿完整链路（待补偿登记、定时扫描、指数退避、死信隔离）。

### 可扩展（面试可讲规划）
1. Redis 单机升级为集群并做热点拆分。
2. MQ 增加分区并行消费、死信队列、延迟重试队列。
3. DB 增加库存分段、批量写与读写隔离。
4. 增加全链路压测与容量规划基线。

### 高频追问短答
1. 100倍先扩哪一层？
答：先扩入口限流和Redis承载，再扩MQ消费与DB写入，优先保护核心链路可用性。

2. 怎么判断重构有效？
答：看拒绝率、下单成功率、消息积压、库存一致性、P99延迟这五个核心指标。

## 6. Redis + Lua 脚本防超卖，你这个 Lua 脚本怎么写的？

### 问题
如何用 Lua 在 Redis 里一次性完成库存校验和一人一单校验，避免并发超卖。

### 主回答（90秒版）
脚本核心是把“查库存、查是否已下单、扣库存、记录下单用户”放到一个原子执行单元里。流程是：

1. 读取库存 key，如果库存不足直接返回失败码。
2. 查询用户是否在订单集合里，如果已存在返回重复下单失败码。
3. 执行库存扣减。
4. 把用户写入下单集合，表示占位成功。
5. 返回成功码。

因为 Lua 在 Redis 内部串行执行，这几步不会被并发打断，所以天然避免“先查后改”并发漏洞。业务层拿到返回码后再决定是否投递订单消息。

### 主回答（30秒版）
Lua 脚本把库存判断、重复下单判断、扣库存、写下单标记放在一次原子执行里。Redis 串行执行 Lua，能从根上避免并发超卖和重复抢购。

### 已实现（项目现状）
1. 已在脚本中实现库存校验与一人一单校验。
2. 已在业务层按返回码做成功/失败分支处理。

### 可扩展（面试可讲规划）
1. 增加库存 key 缺失兜底判断，避免空值比较风险。
2. 增加活动时间窗校验，提前在脚本层拒绝未开始/已结束请求。
3. 增加脚本执行耗时与失败码埋点。

### 示例脚本（可口述）
```lua
local voucherId = ARGV[1]
local userId = ARGV[2]

local stockKey = 'seckill:stock:' .. voucherId
local orderKey = 'seckill:order:' .. voucherId

local stock = tonumber(redis.call('get', stockKey))
if (not stock) or (stock <= 0) then
	return 1
end

if redis.call('sismember', orderKey, userId) == 1 then
	return 2
end

redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, userId)
return 0
```

### 高频追问短答
1. 为什么 Lua 比 Java 里加锁更好？
答：Lua 在 Redis 内部原子执行，网络往返少、并发窗口小，性能和正确性更稳。

2. 返回码怎么设计？
答：通常 0 成功，1 库存不足，2 重复下单，业务层按码分流。

## 7. 集群环境下各节点本地缓存不一致，怎么保障一致性？

### 问题
本地缓存（L1）在多节点部署时天然不共享，如何避免节点间数据不一致。

### 主回答（90秒版）
这个问题要先澄清：本地缓存一致性通常只能做到“最终一致”，很难强一致。

当前项目做法是“写DB后发布缓存失效事件”，由 MQ 消费端统一删除 Redis（L2）并失效消费节点本机 L1；同时链路具备重试、死信、补偿。

这里要注意边界：当前是单队列竞争消费，不是广播模型，所以多节点 L1 仍会存在短暂不一致窗口。

如果要进一步增强，我会做三步：

1. 引入缓存失效广播机制（每节点独立订阅，或 Pub/Sub 广播）：任一节点更新数据后，所有节点都能收到失效事件并删除对应 L1 key。

2. 给 L1 设置更短 TTL 并保留版本号：即使广播偶发丢失，也能快速自然收敛。

3. 关键写路径增加“延迟二次删”或版本校验，进一步缩短脏读窗口。

这样可以在可接受成本下，把多节点本地缓存一致性从“单节点正确”升级为“集群最终一致且窗口可控”。

### 主回答（30秒版）
集群下 L1 一定有不一致窗口。当前是“DB 更新后发失效事件”，由消费者删 L2 + 本机 L1。增强方案是把失效从竞争消费改成广播到所有节点，再配合短 TTL 和版本号实现更快收敛。

### 已实现（项目现状）
1. 写操作后会发布缓存失效事件（MQ）。
2. 消费端会删除 Redis（L2）并失效消费节点本机 L1。
3. 失效链路有重试、死信、补偿机制。
4. L1 有 TTL 机制，可自然过期收敛。

### 可扩展（面试可讲规划）
1. 引入跨节点 L1 失效广播（每节点都消费到失效事件）。
2. 增加延迟双删与版本字段校验。
3. 对热点 key 启用主动推送更新策略。

### 高频追问短答
1. 一定要强一致吗？
答：缓存层通常追求最终一致，强一致成本高且会伤吞吐，是否需要取决于业务容忍度。

2. 广播丢消息怎么办？
答：短 TTL + 周期巡检 + 关键路径版本号三重兜底。

## 8. 如果缓存删除失败，消息队列重试最大次数是多少？超过后如何处理？

### 问题
缓存删除失败后，如何设计重试上限和兜底处理，避免无限重试与数据长期不一致。

### 主回答（90秒版）
当前项目这条链路已经落地：

1. 更新 DB 后，先发布缓存失效事件并登记 pending。
2. 消费端删除 L2/L1 失败时，不直接无限重回主队列，而是进入 retry 队列做延迟重试。
3. 重试采用指数退避（基础 30s），最大重试 8 次。
4. 超过次数会转死信，并保留 pending/dead 记录，供告警和人工/任务补偿。
5. 定时补偿任务每 30s 扫描 pending，继续补偿重发直到收敛或转死信。

所以这里的关键不是“有没有重试”，而是“有上限、有节流、有死信、有补偿闭环”。

### 主回答（30秒版）
项目里缓存失效失败的 MQ 重试已实现：最大 8 次，指数退避延迟重试，超过后进死信并告警，定时补偿任务持续兜底，保证最终一致。

### 已实现（项目现状）
1. 写路径为“先更新 DB，再发布缓存失效事件”。
2. 缓存失效链路已具备：pending 记录、延迟重试、最大重试 8 次、死信隔离。
3. 有定时补偿任务扫描 pending 并重发。
4. L1/L2 仍有 TTL 兜底，可降低长期脏数据风险。

### 可扩展（面试可讲规划）
1. 增加 dead 集合自动告警（短信/IM）和工单联动。
2. 增加补偿成功率、重试分布、死信堆积看板。
3. 针对热点 key 增加优先级补偿策略。

### 高频追问短答
1. 为什么不是无限重试？
答：无限重试会放大故障并挤占资源，必须有上限和隔离通道。

2. 超过次数后是不是就不管了？
答：不会，超过阈值会进 dead 并触发补偿/告警闭环，不会“静默丢弃”。

## 9. 本地缓存和Redis怎么协同？什么时候优先本地缓存？如何保证两级缓存一致性？

### 问题
两级缓存怎么设计访问顺序与失效策略，既要性能又要一致性。

### 主回答（90秒版）
我把本地缓存（L1）和 Redis（L2）定位成“低延迟层 + 共享层”。访问顺序是 L1 -> L2 -> DB。

优先读本地缓存的场景是高频热点读，尤其是短时间内重复访问同一 key，这时 L1 可以显著降低网络开销和 Redis 压力。

如果 L1 miss，再读 Redis。Redis 命中后回填 L1；Redis miss 才回源 DB 并回填 L2/L1。

一致性策略在当前项目是“事件驱动失效”：先更新 DB，再发布失效事件；消费端删除 L2 并失效消费节点本机 L1。由于 L1 不共享，一致性目标仍是最终一致，不是强一致。

为减少不一致窗口，通常配合短 TTL、空值缓存、防击穿策略和可选失效广播。

### 主回答（30秒版）
协同策略是 L1 本地优先，miss 再查 L2 Redis，再 miss 回源 DB。回填顺序是先 L2 再 L1。写路径是先 DB 后发失效事件，由消费端删 L2 + 本机 L1；整体按最终一致收敛。

### 已实现（项目现状）
1. 已实现 L1（Caffeine）+L2（Redis）查询链路。
2. 已实现回填与空值缓存。
3. 写路径是“更新 DB -> 发布失效事件 -> 消费端删除 L2 并失效本机 L1”。
4. 缓存失效链路有重试、死信、补偿机制。

### 可扩展（面试可讲规划）
1. 增加跨节点 L1 失效广播。
2. 增加 key 版本号和双删策略。
3. 增加缓存命中率、回源率监控看板。

### 高频追问短答
1. 什么时候不建议用本地缓存？
答：数据变更极频繁且强一致要求高的场景，不建议重度依赖L1。

2. L1和L2 TTL怎么定？
答：一般 L1 更短、L2 更长，L1追求低延迟，L2追求共享与稳定命中。

## 10. 缓存是怎么设计的？缓存里具体存了什么？key和value是什么？静态信息存了吗？

### 问题
项目缓存整体设计、数据模型和 key/value 约定是什么。

### 主回答（90秒版）
项目是“按业务域拆 key + 按场景选数据结构”的缓存设计。

常见 key 设计：

1. 登录验证码：login:code:{phone}，value 是验证码字符串，短TTL。
2. 登录态：login:token:{token}，value 是用户信息 Hash。
3. 店铺缓存：cache:shop:{id}，value 是店铺JSON或逻辑过期包装对象。
4. 店铺分类：cache:shopType:，value 是分类列表JSON。
5. 秒杀库存：seckill:stock:{voucherId}，value 是库存数值。
6. 秒杀下单集合：seckill:order:{voucherId}，value 是用户ID集合。
7. 分布式锁：lock:*，value 是锁持有者标识。
8. 布隆过滤器：bloom:shop:id，value 是位图结构（由组件管理）。

静态信息是否缓存：会缓存读多写少且允许短时最终一致的数据，比如店铺详情、店铺分类这类准静态信息。对高频变更且强一致要求高的数据，不会盲目强缓存。

### 主回答（30秒版）
缓存按业务域命名 key，按场景选结构：String、Hash、Set、Bloom。典型有验证码、登录态、店铺详情、分类、秒杀库存和下单集合。静态或准静态数据会缓存，强一致高变更数据谨慎缓存。

### 已实现（项目现状）
1. 已有统一 key 常量与命名规范。
2. 已落地登录态、店铺、分类、秒杀库存、下单集合等缓存。
3. 已落地空值缓存、TTL与逻辑过期能力。

### 可扩展（面试可讲规划）
1. 统一 key 版本前缀，支持灰度升级。
2. 统一缓存元数据（来源、版本、更新时间）便于追踪。
3. 增加热点 key 自动识别与预热。

### 高频追问短答
1. 为什么登录态用Hash？
答：字段化读写方便，更新单字段成本低。

2. 为什么店铺详情用JSON字符串？
答：对象读写简单，应用层序列化/反序列化成本可控，适合整体回填。
