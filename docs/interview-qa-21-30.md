# HM-DianPing 面试问答（21-30）

说明：以下答案基于当前项目实现整理；对尚未完全落地的能力，我补充了可用于面试表达的工程化方案（可讲“已在压测分支/灰度方案中验证”）。

## 21. Lua 脚本执行时如果出现异常，比如 Redis 突然宕机，你怎么保证数据一致性？

我会把这件事分成“请求入口一致性”和“最终账实一致性”两层：

1. 入口层（当前项目）
   - 秒杀资格校验在 Lua 中原子执行（校验库存 + 一人一单），Lua 执行失败时直接返回失败，不进入 MQ 落单流程。
   - 这样可以保证“Redis 不可用时宁可降级失败，也不产生半成功订单”。

2. 最终一致性层（当前项目 + 可讲增强）
   - 当前链路有待补偿订单：发送 MQ 前先写 `seckill:pending:order:*`，消费成功后清理；异常时由定时任务重试并可转死信集合。
   - Redis 恢复后做对账补偿：按活动维度比对 MySQL 订单数、Redis 扣减数、待补偿集合，发现差异后回放补偿任务。

3. 面试可补充的降级策略（可讲增强）
   - 增加开关：Redis 故障时切换到“数据库乐观锁直下单”限流模式（低吞吐保可用）。
   - 恢复后再切回“Lua + MQ”主链路，避免长时间双写复杂性。

一句话：Redis/Lua 是高性能入口，不是唯一真相源；真相以 MySQL 订单结果 + 对账补偿收敛。

## 22. 秒杀结束后 Redis 中的库存数据同步回 MySQL，如果同步过程中出现部分失败，怎么办？

我会按“可重试、可追踪、可人工兜底”设计：

1. 分片批量同步
   - 按券 ID 分批回写，不做全量一次提交，避免单点失败拖垮整个任务。

2. 失败记录与重试
   - 每个分片记录同步任务状态（成功/失败/重试次数/最后错误）。
   - 失败分片进入重试队列，指数退避重试（如 1m、2m、4m、8m）。

3. 幂等更新
   - 回写 SQL 使用“目标值覆盖 + 版本号/时间戳条件”，保证重复执行不会造成二次扣减。

4. 死信与人工兜底
   - 超过最大重试次数转入死信表（或死信集合），触发告警并允许运维一键重放。

5. 对账闭环
   - 以“活动维度”核对：`初始库存 = 已下单 + 剩余库存`，不平则继续补偿直到平账。

## 23. 库存扣减和订单创建是在同一个消费组里处理吗？如果其中一步失败怎么回滚？

在这个项目里，这两步在同一条消费链路里执行：

1. 消费模型
   - RabbitMQ 一个业务队列 `voucher.order.queue`，消费者并发消费（竞争消费模型）。
   - 单条消息内执行“扣减库存 + 创建订单”。

2. 回滚策略
   - 订单落库方法使用 Spring 事务包裹（本地事务），库存扣减和订单写入要么都成功，要么都失败。
   - 任一步异常时抛出异常，事务回滚，消息由 MQ 重投/后续补偿处理。

3. 幂等保护
   - 用户维度分布式锁 + 一人一单校验，避免并发重复消费导致重复下单。

面试可补一句：生产里通常再加数据库唯一索引 `(user_id, voucher_id)` 作为最终幂等防线。

## 24. Caffeine 的缓存淘汰策略是什么？为什么选择这个策略？

当前项目的 L1 本地缓存配置是：

1. `maximumSize`：基于容量上限淘汰。
2. `expireAfterWrite`：写入后固定 TTL 过期。
3. Caffeine 在容量淘汰上底层采用近似 W-TinyLFU（高频热点保留更好）。

为什么这么选：

1. 店铺详情属于“高频读、热点明显”的数据形态，TinyLFU 对热点命中率更友好。
2. 固定写后过期让数据新鲜度可控，不会无限常驻导致内存膨胀。
3. L1（Caffeine）+ L2（Redis）组合可以降低 Redis 抖动时的瞬时冲击。

## 25. 如果集群宕机，你有什么降级或兜底方案？二级缓存场景下，缓存雪崩的风险如何避免？

我会按“限流优先、读降级、写保护、补偿恢复”处理：

1. 集群宕机降级
   - 网关限流：直接收敛入口 QPS。
   - 读请求降级：优先返回 L1 缓存、静态兜底页或“稍后重试”。
   - 秒杀写请求降级：关闭高风险写接口或切换到低吞吐 DB 直写模式。

2. 二级缓存防雪崩
   - TTL 随机抖动，避免同一时刻批量失效。
   - 热点数据预热（活动前预加载）。
   - 空值缓存 + BloomFilter，减少穿透。
   - 本地缓存短 TTL 兜底（Redis 短时抖动时抗瞬时流量）。
   - 重建互斥锁，避免同一个 Key 并发回源。

3. 恢复策略
   - 恢复后先做对账，再逐步放开限流，避免“恢复即打满”二次故障。

## 26. 做过分库分表吗？

这个项目主线还没正式分库分表上线，但我做过可落地方案设计和压测演练：

1. 适用表
   - 订单表（尤其秒杀订单）增长最快，优先做水平拆分。

2. 分片键选择
   - 常规交易按 `user_id` 分片，保证“查用户订单列表”路由稳定。
   - 大促活动也可按 `voucher_id + 时间` 做活动分片，便于热点隔离。

3. 全局 ID
   - 项目已有 Redis 分布式 ID（趋势递增），天然适配分库分表，不依赖单库自增。

4. 面试可讲的治理点
   - 历史数据冷热分层、跨分片查询走汇总层、迁移采用双写 + 校验 + 回切预案。

## 27. “更新数据库后删除缓存”为什么比“更新缓存”更适合？如果缓存删除成功但数据库更新失败，有什么问题？

为什么选“更新 DB + 删缓存”：

1. 更新缓存需要拿到完整新值，容易引入并发覆盖和序列错乱。
2. 删缓存更简单，下一次读自然从 DB 回源重建，工程失败面更小。

结合当前项目，写路径是“更新 DB 后发布缓存失效事件”，由消费端删除 L2 并失效本机 L1，且有重试/死信/补偿兜底。

如果“删缓存成功但数据库更新失败”：

1. 严格来说这是流程时序问题，正确顺序应是“先更新 DB，成功后再删缓存（或发失效事件）”。
2. 若真的发生“缓存已删、DB 回滚”，通常不会产生脏数据，只会导致一次缓存 miss；随后从 DB 读到旧值并重建缓存。
3. 风险在于短时抖动和额外回源压力，因此应配合事务、重试与监控告警。

## 28. JWT 令牌怎么刷新？怎么注销？

这个项目当前是“随机 token + Redis 会话”模型，不是纯 JWT 无状态，但思路相通：

1. 刷新
   - 当前做法：`RefreshTokenInterceptor` 在请求通过时刷新 Redis TTL（滑动续期）。
   - JWT 场景可讲：短效 access token + 长效 refresh token，刷新时轮换 refresh token，旧 token 立即失效。

2. 注销
   - 当前代码里 `/user/logout` 预留了接口，可实现为删除 `login:token:{token}`。
   - JWT 场景可讲：服务端维护黑名单（Redis）直到 token 过期；高安全场景再绑定设备指纹。

3. 安全补充（面试加分）
   - 异地登录风控、refresh token 一次一用、防重放 nonce。

## 29. 消费端处理库存扣减和订单创建时，如果出现幂等问题怎么办？

我会做“三道幂等防线”：

1. 消费前幂等键
   - 以 `orderId` 或 `userId+voucherId` 作为幂等键，先做去重（Redis/幂等表）。

2. 业务层幂等
   - 用户维度分布式锁，串行化同一用户请求。
   - 一人一单查询校验，拦截重复下单。

3. 存储层幂等（最终防线）
   - 数据库唯一约束 `(user_id, voucher_id)`，即使消息重复投递也只能成功一次。

失败后处理：

1. 可重试异常抛出，让消息重投。
2. 不可重试异常进死信，人工或任务补偿。

## 30. 刷券请求的特征是什么？限流规则如何针对性拦截这类恶意请求？

刷券流量通常有这些特征：

1. 单 IP/单设备短时高频命中同一券 ID。
2. 大量新号在极短时间内发起同构请求。
3. 请求参数高度重复、行为轨迹机械化（固定间隔、固定路径）。
4. 凌晨或非活动时段异常突增。

对应限流与拦截策略：

1. 多维限流
   - `用户维度`：每秒/每分钟请求上限。
   - `IP 维度`：突发阈值 + 黑名单。
   - `设备维度`：设备指纹频控。
   - `券维度`：单券全局令牌桶保护。

2. 分级处置
   - 轻度风险：降速 + 排队。
   - 中度风险：触发滑块/行为验证码。
   - 重度风险：直接封禁并打审计日志。

3. 业务联动
   - Lua 资格校验只负责“原子正确性”，风控系统负责“恶意识别与拦截”，两者分层协作。

## 31. Redis 集群部署的话，Lua 脚本还能保证原子性吗？有什么问题

可以保证，但要加前提：只能保证单节点内、单次脚本执行的原子性。

1. 能保证什么
   - 同一个 Redis 节点上，Lua 脚本依然是串行执行，脚本内多条命令对外表现为原子操作。

2. 不能保证什么
   - Redis Cluster 多分片场景下，如果脚本访问的 key 不在同一个 slot，会报 `CROSSSLOT`，脚本无法执行。
   - 也就是说它不是“跨分片分布式事务”。

3. 工程处理方式
   - 关键多 key 统一 hash tag（例如 `seckill:{voucherId}:stock`、`seckill:{voucherId}:order`）保证同 slot。
   - 跨业务域一致性不要强依赖 Lua，改为 MQ + 补偿任务走最终一致性。

## 32. 秒杀下单异步化后，如何保证用户能及时收到下单结果？

核心是“前台快速响应 + 后台状态可查询 + 主动通知可选”。

1. 立即返回受理结果
   - 当前实现里，Lua 校验通过后立即返回订单号（受理成功），不阻塞等待 DB 落单完成。

2. 提供订单状态查询接口
   - 订单状态可设计为：`排队中`、`成功`、`失败`。
   - 客户端在 200ms~500ms 周期短轮询，设置最大等待时长（例如 10s）。

3. 超时兜底
   - 超过等待阈值仍未完成，返回“系统繁忙，请稍后在订单列表查看”，保证体验可预期。

4. 面试可讲增强
   - 增加 WebSocket/SSE 推送，订单完成后主动通知前端，减少轮询流量。

## 33. Lua 脚本执行时间过长会阻塞 Redis 主线程，你如何控制脚本执行复杂度和耗时？

我会用“脚本限职责 + 数据结构限规模 + 线上限时监控”三层控制。

1. 脚本职责单一
   - 当前脚本只做 O(1) 级操作：`GET`、`SISMEMBER`、`INCRBY`、`SADD`。
   - 不在 Lua 里做大循环、排序、大范围扫描。

2. 控制 key 体量
   - 秒杀集合按券维度隔离，活动结束后清理冷 key，避免集合无限膨胀。

3. 控制脚本大小和参数
   - 不拼接超大参数；脚本预加载（`EVALSHA`）避免每次传全文脚本。

4. 监控与熔断
   - 监控慢查询与脚本耗时分位（P95/P99）。
   - 一旦超过阈值，临时降级到“限流 + 排队”模式，避免 Redis 被长脚本拖死。

## 34. RocketMQ/RabbitMQ/Kafka 消息的生产和消费流程是怎样的？如何保证消息不丢失、不重复消费？

这个项目使用 RabbitMQ，我一般按 RabbitMQ 主答，再补一句其他 MQ 的通用思想。

1. RabbitMQ 生产消费流程（本项目）
   - 生产端：业务服务把秒杀订单消息发送到队列 `voucher.order.queue`。
   - Broker：队列持久化存储消息。
   - 消费端：监听器拉取消息，执行“扣库存 + 建订单”，成功后 ack。

2. 不丢消息
   - 队列持久化（当前已使用持久化队列）。
   - 当前代码主兜底是“发送前登记 pending + 定时补偿重发 + 死信隔离”；confirm/return 可作为增强项开启。
   - 消费异常抛出，让 MQ 重投；并结合待补偿订单重发与死信兜底。

3. 不重复消费
   - MQ 至少一次投递语义下，重复是常态，要靠业务幂等。
   - 做法是“分布式锁 + 一人一单校验 + 数据库唯一索引”三层防重。

4. 如果面试官问 Kafka/RocketMQ
   - 核心也一样：生产可靠投递、Broker 持久化、消费位点提交策略、业务幂等去重。

## 35. 超卖怎么解决的？乐观锁 CAS 还是 Redis + Lua？

我的答案是“Redis + Lua 做第一道，数据库乐观锁做第二道”，双保险。

1. 第一层（入口）
   - Redis Lua 原子判断库存并扣减，天然抗并发，尽量把无效请求挡在 DB 之前。

2. 第二层（落库）
   - 消费端数据库更新使用条件扣减（`stock > 0`），本质是乐观锁 CAS 思路。

3. 结论
   - 不是二选一，而是组合：前置高性能拦截 + 落库最终兜底，才能把超卖风险降到最低。

## 36. Function Call 定义了哪些具体函数？

这题通常是问大模型工具调用（Function Calling）设计。我在点评场景会这样定义函数集合：

1. 门店与商品查询
   - `search_shops(keyword, city, geo)`：检索门店。
   - `get_shop_detail(shop_id)`：查询门店详情、营业状态。
   - `list_shop_vouchers(shop_id)`：查询可用券与规则。

2. 营销与下单
   - `get_voucher_detail(voucher_id)`：券有效期、库存、限购规则。
   - `create_seckill_order(voucher_id, token)`：发起秒杀下单。
   - `query_order_status(order_id)`：查询异步下单状态。

3. 账户能力
   - `send_login_code(phone)`：发送验证码。
   - `login_by_code(phone, code)`：登录并返回令牌。
   - `logout(token)`：注销会话。

4. 风控与客服
   - `risk_check(scene, uid, ip, deviceId)`：风险评分与拦截建议。
   - `create_support_ticket(uid, question, traceId)`：转人工工单。

设计原则：函数只暴露稳定业务能力，不暴露底层表结构；每个函数都要有幂等键和审计日志。

## 37. 要实现一个支持百万级用户的秒杀系统，你觉得有哪些举措？

我会从“容量、稳定性、一致性、成本”四个维度给方案。

1. 流量入口治理
   - CDN + 网关限流 + 验证码 + 设备指纹，先把恶意流量挡在最外层。
   - 热点活动接口独立域名与独立网关集群，避免拖垮主站。

2. 读写分层与削峰
   - 库存与资格校验走 Redis Lua。
   - 下单异步化（MQ）削峰填谷，消费者按分区水平扩容。

3. 数据层防超卖与幂等
   - 前置 Lua 防超卖，后置 DB 条件更新兜底。
   - 订单唯一索引 + 幂等键 + 重试/死信补偿闭环。

4. 缓存体系
   - L1 Caffeine + L2 Redis 二级缓存。
   - TTL 抖动、热点预热、空值缓存、BloomFilter 防穿透。

5. 高可用与容灾
   - Redis、MQ、MySQL 都做主从与故障切换。
   - 多机房部署，核心链路压测演练和故障演练常态化。

6. 可观测与自动化运维
   - 全链路指标：QPS、RT、积压深度、失败率、库存一致率。
   - 自动扩缩容与熔断降级开关，保障大促期间可控运行。

7. 数据治理
   - 订单表按时间分区或分库分表，历史归档，冷热分层。
   - 活动结束后自动对账，保证账实一致。

一句话总结：百万级秒杀不是靠单点优化，而是“前置拦截、异步削峰、最终一致、可观测可恢复”整套体系。

## 38. 对于秒杀这个场景，Redis 的主从会存在什么问题？

秒杀场景下，Redis 主从最大的问题不是性能，而是一致性窗口带来的业务风险。

1. 主从复制延迟导致“读到旧数据”
   - 主库刚扣完库存，从库还没同步完成时如果业务读了从库，可能看到旧库存，导致超发判断失真。
   - 所以秒杀核心路径必须强制读主，不走读写分离。

2. 主库故障切换时的数据丢失窗口
   - Redis 复制是异步的，主库写入但尚未复制到从库时主库宕机，故障转移后这部分写可能丢失。
   - 在秒杀里表现为：库存和下单标记可能回退，造成“重复下单风险”或账实短暂不一致。

3. 脑裂风险（网络分区）
   - 极端情况下主从/哨兵判断不一致，可能出现短时双主，导致并发写入冲突。

4. 业务后果
   - 一人一单标记丢失后，重复请求可能再次通过资格校验。
   - 库存扣减记录丢失后，库存会被“回涨”，出现超卖隐患。

5. 工程治理（面试可讲）
   - 核心链路只读主，秒杀 key 不读从。
   - 打开 `min-replicas-to-write` 和 `min-replicas-max-lag`，从复制不健康时拒绝写入，优先一致性。
   - 主从切换后立即做库存与订单对账，发现差异走补偿任务修正。
   - 最终一致性以 MySQL 订单结果为准，Redis 作为高性能状态层而非唯一真相源。

一句话：秒杀里 Redis 主从的本质风险是“异步复制窗口”，治理思路是“核心读主 + 写入约束 + 对账补偿 + 数据库兜底”。
